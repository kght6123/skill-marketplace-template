# orch-review-triage

**AIは分類する。実行はしない。** 「対応不要」も含めて🚀を待つ。

スクリプトの場所と実行の鉄則は `orch-core/SKILL.md` を読む。以下 `$ORCH` はその手順で解決したパス。

## 手順

### 1. 指摘を集める

```bash
gh pr view <pr> --repo <org/repo> --json reviews,comments
gh api repos/<org/repo>/pulls/<pr>/comments --paginate
```

### 2. 理解メモと突き合わせる

```bash
node "$ORCH" state get <key>      # commentId から理解メモを引く
```

指摘がメモの仮定や確認事項の回答と矛盾していないかを見る。矛盾していたら「起票者へ」。

### 3. 分類する

| 分類 | 使うとき |
|---|---|
| 修正 | 指摘が正しく、このPRの範囲で直せる |
| 対応不要 | 規約どおり・既存の方針どおりで、変える必要がない |
| 起票者へ | 仕様が未定で、コードだけでは決められない |

迷ったら「起票者へ」。AIが仕様を決めない。

### 4. 対応案を書く

````markdown
<!-- ai-triage v1 review=123456 -->
## 指摘の対応案（@reviewer: Approve＋コメント）
| # | 指摘 | 案 | 理由 |
|---|---|---|---|
| 1 | export.ts:42 fromの検証 | 修正 | 不正値で例外 |
| 2 | 命名が長い | 対応不要 | 規約どおり |
| 3 | 期間上限は？ | 起票者へ | 仕様未定 |

<details><summary>返信案</summary>…</details>

---
<sub>🚀 案どおり ／ 👎 案が違う（番号付きで返信）／ 😄 後回し</sub>
````

### 5. 投稿する

```bash
node "$ORCH" post --key <key> --kind triage --pr <pr> --body /tmp/triage.md
```

ここで止まる。🚀が付くまで、修正もスレッドの解決も返信もしない。

### 6. 🚀のあと

`orch next --mode build` が `apply-triage` を返すので、`orch-implement` が修正する。
対応が終わったらこのコメントを折りたたむ。

## 仕様の質問の扱い

「起票者へ」に分類した指摘は、Issue の理解メモの確認事項に回す。
回答が来るまでそのPRは止める。PRのスレッドで仕様を決めない。

## 注意事項

- 「対応不要」も🚀を待つ。勝手にスレッドを解決しない
- 返信案は書くが、投稿は🚀のあと
- レビュアーの指摘を否定するときほど、理由を1行で具体的に書く
- 指摘が理解メモと矛盾している場合は、メモ側が古い可能性も併記する
