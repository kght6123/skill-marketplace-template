# AI開発オーケストレーション 全体像

複数プロジェクトを並行してAIに開発させる際、人間の理解・レビュー・テストがボトルネックになる問題への対処。
基本方針は「人間の処理量を上限にして、AI側をそれに合わせる」。

- 人間が読むのはコードだけでなく、その前に「意図」（理解メモ）
- AIは分類しても実行しない。承認・マージ判断は必ず人間
- 状態遷移・上限判定・並び順はすべてスクリプトで決定的に処理。AIは生成のみ
- 行列が満杯ならAIの新規投入を止める

## 流れ

```
Issue本文に🚀
  → 規模判定 ─大→ 分割案 →🚀→ Sub Issue作成 → 各Sub Issueの規模判定へ（深さ3まで）
            └小→ 理解メモ → 起票者の回答 →🚀→ 実装
                                              → セルフレビュー →🚀→ レビュー依頼
                                              → 他エンジニアのApprove → 自動マージ
```

| サイクル | 内容 | スキル |
|---|---|---|
| tick | sync → 理解メモ（最大3件） | `orch-run`（tickモード）→ `orch-issue-memo` |
| build | sync → WIP判定 → 実装（1件） | `orch-run`（buildモード）→ `orch-implement` |
| merge-train | 条件を満たしたPRを順にマージ | `orch merge-train`（AIの判断なし） |

## レビュアー（orch.config.json の reviewers）

- `assign: one` は依頼中件数が最少の人。同数なら設定の並び順（スクリプトで決定的に選ぶ）
- 同じスタックのPRは2本目以降も同じレビュアー（文脈を知っている方が速い）
- 全員が上限なら依頼を保留し、`orch next` に「レビュアー待ち」として表示

## WIP上限（orch.config.json の wip）

行列ごとに上限を持ち、超えたらその行列を増やす処理を止める。
承認待ちメモが上限なら新規Issueのメモ生成を後回しに、レビュー待ちPRが上限なら実装に着手しない。
「AIが作るほど人間の行列が伸びる」状態を仕組みで防ぐ。

## next-task の並び順（他人を待たせているもの → 完了に近いもの）

1. 指摘の対応確認 2. 判断が必要な競合 3. セルフレビュー 4. 分割案
5. 理解メモ 6. その他のneeds-human 7. 本文スタンプ候補 8. 事後確認

同種内では、ブロックしている件数 → Milestoneの期限 → 待ち時間の順。

**マルチタスク回避**

- 一度プロジェクトを選んだら、その行列が空になるかタイムボックス（既定45分）まで同じプロジェクトを優先
- 他エンジニア待ちの指摘だけ別プロジェクトから割り込み可
- 事後確認は1日1回（既定17時）にまとめる
- 順調に動いているAIの作業は表示しない。出すのは人間の判断が必要なものと止まっている理由だけ
- `orch next --minutes 15` で空き時間内に終わる1件を選ぶ

## マージ条件の扱い

順番も条件のうち。セルフレビューの承認（承認用コメントのスタンプ）が
現在の head に対して付いていなければマージしない。他エンジニアが先に Approve しても、
セルフレビューを飛ばして進めない。

判断できない状態は「止める」側に倒す。未解決のレビュースレッドを取得できない、
CIの状態が読めない、PRを取得できない、のいずれもマージしない理由になる。
GitHub の一時エラーで自動マージが走るのが、この仕組みで一番まずい壊れ方。

## 前提と注意

- PR作成者は自分のPRをApproveできないため、セルフレビューの承認はスタンプで代替している
- ブランチ保護で「承認レビュー必須」が有効な場合、スタンプではその条件を満たせない
- 「古い承認を取り消す」設定が有効だと、プッシュのたびに他エンジニアの承認が外れる
- ローカル実行のため、実行するマシンの電源が入っていないと動かない
